⚠ Six non-negotiable constraints

Every design decision, every line of code, every commit is checked against these six rules. If a change violates any of them, it's rejected — no exceptions, no "but it makes benchmarks faster".

  1. Root only. Magisk / KernelSU. We do not build a non-root fallback path. Root is the required setup, and the README says so.
  2. Hardware safety first. CPU ≤ 75 °C, GPU ≤ 70 °C — always. Auto-revert to stock on breach. Never disable thermal entirely; only raise trip points by a maximum of +5 °C.
  3. Boot-loop protection. A watchdog counts failed boots. Three in a row → automatic rollback to stock profile.
  4. Offline only. No telemetry, no analytics, no network calls. The APK does not declare the INTERNET permission. The Magisk module does not phone home.
  5. Lightweight. APK + Magisk module combined < 15 MB. The TFLite model alone < 2 MB.
  6. Everything revertible. Every tweak has a matching revert function. Every script is idempotent — safe to run twice.

The problem

In 2020 Samsung sold the Galaxy A11 for about $150. It has a Snapdragon 450 — an SoC Qualcomm designed in 2017 for mid-range phones. 8 Cortex-A53 cores at 1.8 GHz. 3 GB of RAM. An Adreno 506 GPU. On paper, it runs Android. In practice, after two or three years of One UI Core updates, it doesn't anymore.

Tap an app icon. Wait four seconds. The keyboard takes two seconds to appear. Switching between two apps reloads both. Games that ran at 30 FPS now stutter at 18. This isn't because the hardware is broken — it's because the software stack was tuned for devices with 8 GB RAM and a big.LITTLE CPU, and Samsung's aggressive background killing + Android's default VM tuning are fundamentally mismatched with SDM450's capabilities.

The hardware can still do more. It's just configured wrong.

The vision

PerfCore is the last thing you install on an old Snapdragon phone before you finally give up on it. It's a root-only Magisk module + companion app that:

  • Rewrites the scheduler, VM, LMK, ZRAM, I/O, and GPU policies to match what an SDM450 can actually sustain.
  • Uses a tiny on-device AI model to swap between four tuning profiles (GAMING / MULTITASK / IDLE / THERMAL_EMERGENCY) based on what you're actually doing right now.
  • Never breaks the device. Every tweak has a hard ceiling, an auto-revert, and a boot-loop watchdog. The worst-case outcome is "it uninstalls itself and you're back on stock".
  • Never phones home. No telemetry, no analytics, no accounts, no ads, no internet permission.
  • Is distributed on GitHub, not the Play Store, because rooting a device to make it faster is not something Google should have opinions about.

What "success" means

Not "10× faster benchmarks". That's marketing. Real success, measurable, on the A11:

What we are NOT building

  • Not a cleaner / booster / RAM-freeer. Those are scams. Free RAM is wasted RAM. We tune how RAM is used, not how much is free.
  • Not a custom kernel. We're using Samsung's stock kernel, just tuning it. Custom kernels come in v3 (see Future Plans).
  • Not a game booster / cheat engine. No FPS unlock hacks, no anti-cheat bypass. Just legitimate sysfs tuning.
  • Not a paid app, not a subscription, not a "pro" tier. Free, open-source, on GitHub.
  • Not a general-purpose tuner. The primary target is SDM450. We support SDM439, SDM660, SDM665, SDM680, SDM695 as secondary (Phase 5+). We do not promise results on MediaTek or Exynos.

The two-person rule

There are two of us. That means:

  • Every commit is reviewed by the other person (even just "looks fine, push").
  • No one ships a sysfs write to a live device unless it has been tested on the A11 first.
  • If we disagree on a design decision, the person whose phase it belongs to wins — but the other person's objection goes in the commit message.
  • If we get stuck for more than 48 hours on something, we scope it down or defer it. Momentum matters more than perfection.

How It Works

The full mental model of the project. Read once, refer back often. No prerequisite knowledge assumed.

1. What is root, and why do we need it?

On a normal Android phone, apps run in a sandbox. They can't read files outside their own folder, they can't call system APIs without the OS's permission, and they definitely can't write to kernel parameters. This is by design — it's what keeps your banking app safe from a sketchy flashlight app.

Root is when the OS's superuser account (UID 0) is accessible to you. Every Android kernel has UID 0 — it's how the OS itself controls hardware. Root just means you get to use it.

We need root because the tuning we do is kernel-level. Writing to /sys/devices/system/cpu/cpufreq/policy0/schedutil/rate_limit_us is not something the OS lets a normal app do — it's a direct kernel parameter. Only UID 0 can touch it.

There is no workaround. No "rootless" version of PerfCore. No ADB-based workaround that survives a reboot. If you don't have root, you're not the target audience.

2. What is Magisk, and what's a "module"?

Magisk is the most popular way to root an Android phone today. It works by patching the boot image — your phone's kernel is unmodified, but at boot, Magisk injects a small init binary that gives you root and hooks the filesystem.

A Magisk module is a zip file that Magisk unpacks into /data/adb/modules/<name>/. It contains three important files Magisk runs automatically:

  • post-fs-data.sh — runs very early at boot, after /data is mounted but before most system services start. Good for VM tuning, ZRAM setup, I/O scheduler changes. Do not run CPU governor tuning here — cpufreq isn't initialized yet.
  • service.sh — runs late at boot, after bootanim exits. Good for CPU governor, GPU, thermal. Runs as root.
  • uninstall.sh — runs when the module is removed. Must restore the device to stock. This is our safety net.

Everything else in the module folder — our bin/*.sh scripts, profiles, the AI daemon — is just data. Magisk doesn't touch it; our scripts call it.

KernelSU is an alternative to Magisk. Same module format, same lifecycle. Our module works on both — we do not depend on Magisk-specific APIs.

3. What is sysfs?

Linux exposes most of its runtime configuration as files under /sys. Reading a file gives you the current value; writing to it changes the setting. It's not a config file — it's a live interface into the kernel.

Example: /sys/devices/system/cpu/cpufreq/policy0/scaling_governor

$ cat /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
schedutil

$ echo performance > /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
$ cat /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
performance

Some sysfs files only accept specific values (you can't set a governor to "banana"), some are read-only, some don't exist on your kernel. Our code always checks existence and write-permission before writing. If a tunable isn't present on this specific A11 build, we log skip:not-present and move on. We never crash on a missing file.

4. CPU governors — what is schedutil?

A CPU governor is the kernel component that decides what frequency to run the CPU at, based on current load. On SDM450 you'll typically see these available: schedutil performance powersave.

  • performance — pins CPU to max frequency. Fastest, but battery dies in 2 hours. Never use this permanently.
  • powersave — pins CPU to min frequency. Battery lasts forever, phone feels broken. Never use this.
  • schedutil — the modern Android governor. Reads the scheduler's load estimate every tick and picks frequency accordingly. This is what we use.

schedutil has a tunable: rate_limit_us. It controls how often schedutil is allowed to change frequency. Default is ~10,000 microseconds (10 ms). By setting it to 0, schedutil re-evaluates on every scheduler tick (~4 ms). More responsive, slightly higher power draw. That's the tradeoff we accept.

There's also uclamp_min — a "floor" on the CPU capacity that the scheduler will give to a task group. If we set uclamp_min = 700 on the top-app cgroup (the currently-visible app), the scheduler guarantees that app gets at least ~68% of CPU capacity. It doesn't pin the CPU, it just biases decisions. When the app goes to background, uclamp goes back to 0. This is how we get foreground responsiveness without baking the whole system at high frequency.

5. Kernel scheduler tunables

Beyond CPU frequency, the scheduler itself has tuning knobs under /proc/sys/kernel/. The three we touch:

  • sched_min_granularity_ns (default 3,000,000 = 3 ms) — minimum time a task runs before it can be preempted. Lower = more responsive to bursts, more context switches. We set 1,000,000 (1 ms) so foreground tasks don't get stuck behind background tasks.
  • sched_migration_cost_ns (default 500,000) — how "expensive" it is to migrate a task to another CPU. On a single-cluster SoC, migrating is cheap (all cores share cache). We keep it at 500,000 — no change needed, but documented for reference.
  • sched_nr_migrate (default 32) — how many tasks can be migrated at once during load balance. We keep it at 32 — increasing it costs latency more than it saves.

Core offlining: Some tuners turn off cores to "save battery". On SDM450 this is actively harmful — all 8 cores are identical A53s, so offlining one just makes the remaining seven hotter and slower. We do not offline cores. Ever.

6. Memory — LMK vs LMKD vs PSI

Android has to kill apps to make room for new ones. There are three ways this can happen, and we have to detect which one your kernel uses:

  • Classic LMK — /sys/module/lowmemorykiller/parameters/minfree. You set six thresholds. When free RAM drops below a threshold, apps below the corresponding oom_adj level get killed. Old, predictable, still works.
  • PSI LMKD — /proc/pressure/memory. Modern Android (10+) uses kernel-provided Pressure Stall Information. Instead of "kill when RAM is low", it says "kill when memory allocation stalls are happening at this rate". Tuned via ro.lmk.* properties. This is what One UI Core on A11 mostly uses.
  • LMKD in userspace — lmkd daemon reads PSI and decides. Uses ro.lmk.* props.

We cannot just pick one and apply it. If we write to minfree on a PSI kernel, nothing happens (wrong interface). If we write ro.lmk.* props on a classic kernel, nothing happens either. Phase 2 starts with detect.sh which figures out which one is live, and the tuning branch follows that.

7. ZRAM — compressed swap

ZRAM is a block device that lives in RAM. You write to it, it compresses your data, and stores the compressed version back in RAM. When you read, it decompresses transparently. Net effect: you get more usable RAM, at the cost of CPU cycles.

On a 3 GB device, having a 1.8 GB ZRAM (60% of MemTotal) lets Android hold ~50% more apps in the background before killing them. Compression algorithm matters:

  • lzo — old, fast decompress, mediocre ratio. Meh.
  • lz4 — our pick. Fastest decompress (which is what matters — reads block UI), decent ratio.
  • lz4hc — better ratio, slower compress. Good fallback.
  • zstd — best ratio, slowest on SDM450's A53 cores. Only if lz4 not available.

On A11, ZRAM is already enabled with lzo by default and sized ~1 GB. We resize to 1.8 GB and change to lz4 (if available). This is safe — ZRAM resize is a standard swapoff / reset / swapon cycle.

8. I/O scheduler

The I/O scheduler decides how read/write requests to storage are ordered and merged. eMMC 5.1 storage on A11 is the slowest part of the system. Bad scheduling makes app launches feel laggy even when the CPU is idle.

  • noop — pure FCFS, no reordering. Fine for SSDs that do their own scheduling.
  • deadline — our pick for A11. Every request gets a deadline; closest-to-deadline requests are served first. Balances throughput vs latency.
  • cfq — Completely Fair Queuing. Fair across processes, but overkill for phones and adds latency. Stock on A11.
  • bfq — even more complex, higher latency. Not on this kernel.

read_ahead_kb controls how much extra data the kernel pre-reads on each I/O. Default 128 KB is too small for eMMC; we set 2048 KB, which matches the read-cache burst size. Feels noticeably faster on app cold-starts.

9. GPU tuning (Adreno 506)

Adreno GPUs are controlled via /sys/class/kgsl/kgsl-3d0/devfreq/. The two governors you care about:

  • msm-adreno-tz — Qualcomm's default. Uses a thermal-zone-aware heuristic to pick GPU frequency. Default choice, keep it.
  • performance — pins GPU to max frequency. Hot. Only use during gaming sessions.

Our AI daemon swaps to performance only when it detects gaming (foreground package is a known game AND battery temp is below 45 °C). Outside gaming, we leave it on msm-adreno-tz. If gaming raises the temp above 70 °C, GPU auto-reverts to msm-adreno-tz immediately.

We never lock max GPU frequency permanently. Ever. Adreno 506 gets to 90 °C quickly and that damages the SoC.

10. Thermal

SDM450 has several thermal zones exposed at /sys/class/thermal/thermal_zone*/. Each zone has a temp (millidegrees C) and a trip_point_N_temp. When a zone crosses a trip point, the thermal HAL takes action (throttle CPU, throttle GPU, cap charging, etc).

Our approach:

  • Read all zones, identify CPU and GPU zones by name (often cpu-0-0-usr, gpuss-0-usr).
  • Raise trip points by +5 °C, max. This delays throttling slightly, giving us more headroom before the SoC heats up. Not a bypass — just a small delay.
  • Never disable thermal. Never set a trip to disabled. Ever.
  • Hard ceiling check: a small loop every 5 seconds reads CPU temp. If > 75 °C, immediately revert all tuning and let the stock governor cool it down. Log THERMAL_EMERGENCY to the applied log.

11. The AI daemon

This is the "smart" part. A small binary (Kotlin or Go) that runs as a background service, waking every 2 seconds, doing this cycle:

1. Collect features:
   - foreground_package: e.g. "com.whatsapp"
   - screen_state: on / off
   - battery_temp: from /sys/class/power_supply/battery/temp
   - cpu_load_2s: from /proc/stat delta over 2s
   - ram_pressure: from /proc/pressure/memory
   - charging: from /sys/class/power_supply/battery/status

2. Run TFLite model → outputs one of:
   - GAMING
   - MULTITASK
   - IDLE
   - THERMAL_EMERGENCY

3. If confidence < 0.7, fall back to rule-based decision:
   - temp > 70 → THERMAL_EMERGENCY
   - fg is game → GAMING
   - screen off → IDLE
   - else → MULTITASK

4. Apply profile → write sysfs values for that profile.

5. Log the decision and confidence.

Each profile is a set of sysfs values. GAMING = GPU performance + uclamp boost + aggressive read-ahead. IDLE = conservative schedutil + GPU powersave. Etc.

Over time, the daemon also records which profile produced the best user-perceived result (measured by "did the user interact with this app within 5 seconds of switching to it?"), and stores it in a Room DB. Next time the same app opens, it prioritizes the profile that worked.

12. The boot-loop watchdog

Bad tuning can prevent boot. To prevent bricking:

  • The module contains bin/watchdog.sh.
  • Every successful boot increments a counter: /data/adb/perfcore/boot_ok_count.
  • If boot fails (kernel panic, bootloop), the counter doesn't increment.
  • If the module's service.sh detects 3 consecutive failed boots (counter unchanged), it:
  • Renames the module folder with a .disabled suffix (Magisk respects this — module won't load).
  • Logs SAFETY: auto-disabled after 3 failed boots.
  • Requires the user to manually re-enable from Magisk app.

This guarantees: worst case, the module disables itself and you boot stock. No soft-bricks. Ever.

13. Knox, on the A11 specifically

Samsung's Knox is a hardware-backed security framework. On the A11, ro.config.knox = v30. Knox 3.0 does several things:

  • Trips a hardware fuse when you unlock the bootloader. Once tripped, Samsung Pay, Secure Folder, and some banking apps stop working. This is unavoidable — but it's already tripped if you're rooted.
  • Reverts certain system properties at boot if they don't match expected values. Specifically, some ro.* properties are watched. Setting them from post-fs-data.sh usually works because we're earlier than Knox's check.
  • Does NOT revert sysfs writes. Writing to /sys/devices/... is invisible to Knox. Our tuning is safe.

Where we use property writes (ro.lmk.*), we wrap them in a Knox check: if ro.config.knox is not 0 or empty, we skip those writes and log skip:knox. Not because it'll break, but because Knox may silently revert them 30 seconds later, causing our state tracking to be wrong.

14. Idempotency — why every script is safe to re-run

Every tune-*.sh follows this pattern:

if [ -w "$path" ]; then
  old=$(cat "$path")
  echo "$new_value" > "$path"
  new=$(cat "$path")
  log "$path" "$old" "$new" "$([ "$new" = "$new_value" ] && echo ok || echo fail)"
else
  log "$path" "-" "-" "skip:not-present"
fi

Run it once: you see old=10000 new=0 status=ok.
Run it again: you see old=0 new=0 status=ok.

Same system state. New log line. No drift. This matters because:

  • The daemon might call tune-cpu.sh --uclamp 700 every few seconds. It must never corrupt state.
  • After a reboot, sysfs resets to stock; the script re-applies. Idempotency = safety.
  • If a human runs the script while tuning, nothing breaks.

Path

Stock (A11)
100 (Android default)
PerfCore value
60
Why
Android's aggressive swappiness pushes anonymous pages to ZRAM early, which is CPU-costly on A53. 60 balances swap pressure vs compress cost.

ZRAM

comp_algorithm

Path
/sys/block/zram0/comp_algorithm
Stock (A11)
[lzo] lz4 lz4hc (lzo active)
PerfCore value
lz4
Why
lz4 decompresses ~3× faster than lzo. Read latency from ZRAM drops from ~40 µs to ~12 µs. The extra CPU cost on compress is unnoticeable.
Verify
cat /sys/block/zram0/comp_algorithm
Rollback
Requires swapoff + reset + swapon cycle. Script does this. Manual: swapoff /dev/block/zram0 && echo 1 > /sys/block/zram0/reset && echo lzo > /sys/block/zram0/comp_algorithm && swapon /dev/block/zram0
Risk
Requires swapoff first. If script forgets, algorithm change is silently rejected. Idempotent script always does the cycle.
ZRAM

disksize

Path
/sys/block/zram0/disksize
Stock (A11)
~1 GB (varies)
PerfCore value
60% of MemTotal ≈ 1.7 GB
Why
Bigger ZRAM holds more apps in compressed state. Trade: more CPU on compress, more battery drain. 60% is the balance point for 3 GB RAM.
Verify
cat /sys/block/zram0/disksize then free -m
Rollback
Requires full cycle: swapoff → reset → resize → set algorithm → swapon.
Risk
If disksize > 80% of RAM, device may fail to boot due to ZRAM initialization eating RAM. Guarded by 60% cap in script.

Testing

Every phase has a checklist. Nothing ships without all boxes ticked. No exceptions.

Golden rules

  1. Test on the actual A11. Not an emulator. Not another Samsung. The A11.
  2. Test from stock every time. Before testing a new build, uninstall the old module, reboot, confirm stock.
  3. Log everything. Screenshots of every cat output. Every applied.log snapshot.
  4. Break it on purpose. After passing, corrupt one value manually and verify the revert works.
  5. Benchmark before AND after. Cold-start times, FPS, RAM at idle. Both numbers, not just the after.

Benchmark methodology

Same methodology for every test. Same device state. Same ambient temperature (~25 °C). Same battery level (80–100%).

Cold-start test

  1. Force-stop target app: adb shell am force-stop <pkg>
  2. Wait 3 seconds
  3. Launch: adb shell am start-activity -W -n <pkg>/<activity>
  4. Record TotalTime from output
  5. Repeat 3 times, take median

Test apps: Chrome (com.android.chrome), WhatsApp (com.whatsapp), Gallery (com.sec.android.gallery3d).

FPS test

  1. Launch target game
  2. Play for 3 minutes
  3. Record FPS from dumpsys SurfaceFlinger --latency
  4. Record max temp from /sys/class/thermal/thermal_zone*/temp

Target game: Subway Surfers (2D, runs well on Adreno 506).

RAM at idle

  1. Boot fresh
  2. Leave screen on, do nothing for 10 minutes
  3. adb shell dumpsys meminfo | head -20
  4. Record Free RAM, Used RAM, Cached

Risks & Safety

What can go wrong, how likely, and what we do about it. Read this before every commit that touches sysfs.

Risk classification

SeverityMeaningResponse
CriticalHardware damage, permanent brick, or data lossMust have auto-revert, watchdog, or revert-first design. No exceptions.
HighBootloop, unstable device, needs manual interventionMust be tested on A11 before merge. Must have documented revert.
MediumDegraded experience, battery drain, thermal throttleDocumented, monitored, tunable. Revert path documented.
LowCosmetic, isolated feature broken, minor latencyFix when it comes up. Not blocking.

Known risks (SDM450 / A11 specific)

Critical

  • Critical Disabling thermal entirely. GPU hits 90 °C → permanent damage. Mitigation: script never disables thermal. Ever. Trip points +5 °C max. Auto-revert on > 70 °C GPU.
  • Critical Pinning CPU to max freq permanently. Battery dies in ~90 min; SoC overheats; eventual permanent degradation. Mitigation: no permanent locks. Only foreground uclamp boost, which is released on background.
  • Critical Writing garbage to thermal trip points. e.g. echo 0 > trip_point_0_temp. Mitigation: script reads stock first, clamps to max(stock, stock + 5000), verifies by read-back.

High

  • High Bootloop from bad post-fs-data.sh. Runs before boot animation. If it hangs, device appears bricked. Mitigation: post-fs-data.sh has set -e off (so one failure doesn't kill the boot), wraps everything in timeout 5.
  • High Wrong LMK branch. Writing to minfree on PSI kernel = no-op, but if we later write to ro.lmk.* on classic kernel, we could brick. Mitigation: detect.sh runs before any LMK write. If detection is none, skip LMK entirely.
  • High ZRAM resize fails silently. disksize write ignored because swap still active. Mitigation: always swapoff first, verify cat disksize after write.
  • High Knox reverts a critical property. ro.lmk.* property set successfully, then reverted 30 s later. Mitigation: read-back verification at +35 s. If reverted, log skip:knox and continue.

Medium

  • Medium Deadline scheduler not supported. Falls back to cfq / noop / stock. If none, log and skip. Never force.
  • Medium Read-ahead too large. Wastes page cache. 2048 is tested safe on 3 GB.
  • Medium SurfaceFlinger 1008 crashes UI. Mitigation: default OFF. Never enable automatically. Documented "advanced users only".
  • Medium Battery drain from daemon. If daemon wakes every 2 s and does heavy work, drain > 2%/h. Mitigation: feature collection is O(1) reads; inference < 15 ms. Battery logged and benchmarked.
  • Medium AI profile swaps cause jank. Switching governor mid-frame. Mitigation: daemon only swaps on app transitions, not within an app. Hysteresis: must be stable for 2 cycles before swapping.

Low

  • Low Some tunables not present. Log skip:not-present. Not a failure.
  • Low Applied.log grows large. Rotates at 1 MB. Older logs archived.
  • Low Config.json corrupted. Default is recreated on next boot. Logs the incident.

Data safety

PerfCore never touches user data. Specifically:

  • Does not read or write /data/data/* (app data)
  • Does not read or write /sdcard/* (user files)
  • Does not modify bootloader, recovery, or partition table
  • Only touches: /proc/sys/*, /sys/*, /data/adb/perfcore/*, /data/adb/modules/perfcore/*

Boot-loop recovery procedure

If the device won't boot after flashing PerfCore:

  1. Wait for watchdog. Device boots stock after 3 failed attempts (module auto-disables).
  2. If it boots: from Magisk app, uninstall module → reboot. Fixed.
  3. If watchdog fails: boot into recovery (Power + Volume Up while plugged in).
  4. From TWRP or recovery file manager: rm -rf /data/adb/modules/perfcore. Reboot. Stock.
  5. Worst case: reflash stock firmware with Odin. Loses root, but recovers the phone. This should never happen — watchdog exists precisely to prevent it.

Thermal ceiling policy (absolute)

  • GPU: 70 °C — measured from the GPU thermal zone
  • Battery: 45 °C — measured from /sys/class/power_supply/battery/temp

These are not targets. They're ceilings. Trigger auto-revert on ANY of them.

About

PerfCore is a root-only Android performance module for low-end Snapdragon devices. Primary target: Samsung Galaxy A11 (SDM450). Distributed on GitHub, not the Play Store. Not affiliated with Google, Qualcomm, or Samsung.

This workspace is a static site. No server, no analytics, no cookies. Data lives only in your browser's localStorage. Export regularly.
